## Ключевой паттерн — Root-Level Overlay (BUG-53 + BUG-08)

**Два бага подряд с одной корневой причиной.** Когда overlay живёт внутри view, который является **источником** `currentScreen` transition, `HexboundApp` cross-fade'ит source наружу вместе с overlay'ем — destination view (`OnboardingCinematicView`, `ArenaDetailView`) синхронно декодит крупные JPEG на main thread → 1–3 секунды чёрного `bgAbyss` без loading UI.

**Симптом ≠ корень.** Оба раза симптом выглядел как "слишком долго загружается экран". Корень — **gap в UI**: старый overlay уже снят, новый ещё не нарисован, и декод backdrop'а блокирует main thread.

**Решение как паттерн** (закреплено в `Hexbound/CLAUDE.md` → "Root-Level Overlays"):
1. Флаг на `AppState` (`isForgingHero`, `showDailyLogin`)
2. Reusable `XxxOverlayView` в `Views/Auth/` или `Views/Components/`
3. Mount at root в `HexboundApp.swift` с `zIndex`
4. `.animation(.easeInOut(duration: 0.3), value: appState.isXxx)` рядом с `currentScreen` animation
5. VM поднимает флаг **до** API call, опускает **после** `Task.sleep(350ms)` на settle
6. `defer { isCreating = false }` — никогда не полагаться на view unmount

**Текущий zIndex-стек** (зафиксирован в CLAUDE.md): Loading 100 → LevelUp 120 → DailyLogin 150 → HeroForge 200 → SessionExpired 250.

## Лессон 2 — ViewModel state leak via missing `defer`

`OnboardingViewModel.createCharacter()` в оригинале **никогда** не сбрасывал `isCreating = false` на success-пути — полагался на view unmount. Error-path сбрасывал. Это типичный анти-паттерн SwiftUI: View struct не имеет deinit-гарантий, а если тот же VM инстанс переиспользуется — флаг течёт forever.

**Фикс-паттерн:**
```swift
isCreating = true
defer { isCreating = false }
do {
  // ... await API ...
} catch { /* ... */ }
```

`defer` срабатывает на всех exit path'ах (success, catch, early return, throw, cancellation).

**Добавлено в guardian**: pitfall `ViewModel isLoading cleanup via defer` с примером incident'а.

## Лессон 3 — Синхронный `Image(named:)` в destination screen

Root cause BUG-08 — `OnboardingCinematicView` имеет `Image("bg-shop")` + `Image("onboarding-city-panorama")` прямо в `body`, НЕ через `CachedAssetImage`. Плюс `scheduleReveal(delay: 0.6)` добавляет 600ms перед первым panel'ем → итого 1.5–2 сек main-thread freeze.

**Добавлено в guardian**: pitfall `Inline loading overlays with synchronous Image(named:) decode`. Сканером ловить тяжело (нужен allowlist тяжёлых ассетов) — пока оставлено как manual review rule. Возможная автоматизация: grep по `Image("(bg-|onboarding-|landing-)` вне `CachedAssetImage`, посчитать размер соответствующего PNG в xcassets, warn если > 200KB.

## Лессон 4 — Dead state после refactor (self-caught CDO)

При создании `HeroForgeOverlayView` я перенёс `@State private var forgeGlow = false` из старого inline overlay, но ничего на него не биндилось — чистый dead state. Поймал сам на CDO-скане перед финальным отчётом, убрал.

## Лессон 6 — TypeScript `let` narrowing не переживает async closure

Коммит `769a1ea`. Vercel упал с:
```
./src/app/api/inventory/equip/route.ts:59:18
Type error: Type 'string | null' is not assignable to type 'string | undefined'.
```

**Root cause:** `let character_id: string | null = null` hoisted вне try/catch (чтобы catch-блок ALREADY_EQUIPPED recovery мог доступиться). После null-check TS narrowed его в локальной области, НО внутри `prisma.$transaction(async (tx) => { ... })` closure narrowing теряется — TS не может доказать, что `let` не перезаписался к моменту реального вызова callback'а.

**Фикс:** после null-check captured в `const charId: string` / `const invId: string`. Эти `const` используются в transaction closure и в post-transaction вызовах. Catch-блок по-прежнему читает hoisted `let character_id` для ALREADY_EQUIPPED recovery.

**Кодифицировано** в `oracle/SKILL.md` секция "TypeScript Strict Mode" — hoisted-let + async-closure narrowing pattern с incident reference и fix pattern. Scanner check можно сделать: grep по `let\s+\w+:\s*\w+\s*\|\s*null` в route.ts, если в том же файле есть `prisma.$transaction(async` → warn.

## Лессон 8 — Client-side validation mirror для мгновенного UX

Коммит `3c67478` (BUG-63). ItemDetailSheet раньше слал equip-запрос на сервер и показывал toast по ошибке. Теперь делает **client-side копию** логики `backend/src/app/api/inventory/equip/route.ts` (level gate, class restriction, broken-item gate) и отключает EQUIP-кнопку + красит "Required level" в красный **до** запроса.

**Паттерн:** когда server validation возвращает детерминированный ответ из данных, которые уже есть у клиента (playerLevel, playerClass, item.requiredLevel, item.classRestriction), — зеркалить проверку на клиенте. Это не замена серверной валидации (сервер всё равно финальный авторитет), а **instant feedback** чтобы не показывать ошибку через 300ms round-trip.

**Риск:** drift между client- и server-copy правила. Когда серверное правило меняется, оба файла надо обновить.

**Не кодифицирую как обязательное правило** — это паттерн для high-frequency interactions (equip, quick buy, sort), не для всего подряд. Но добавлю placeholder в "Tasks for next retro", чтобы пересмотреть через 2-3 таких зеркалирования и решить — оформлять как convention или оставить ad-hoc.

## Лессон 9 — Крупные рефакторы с associated-value добавлениями проходят чисто

Коммит `d4450b4` добавил `body: [String: Any]?` третий параметр в `APIError.clientError(code, message, body)`. Это затронуло **25+ pattern-match sites** в ShopService, DungeonService, InventoryService, BattlePreloader, BattlePassService, FortuneWheelViewModel, ShellGameViewModel, ReferralSectionView, SupabaseAuthClient. Swift exhaustiveness checking заставил обновить все сайты, CI прошёл с первого раза, CDO: CLEAN.

**Урок:** Swift pattern-match exhaustiveness — best protection от broken refactor'ов. Когда добавляется associated value в enum case, компилятор обязывает обновить ВСЕ pattern-match'и. Контраст с runtime-языками (TS narrowing выше), где аналогичная ошибка может проскочить до прода.

**Ничего не кодифицирую** — это свойство языка работает, paттерн не требует правил, только заметка "Swift enum refactor = safe".

## Лессон 10 — Scanner false negative: init-overwrite был бы пойман, если бы сканер существовал

Обратная сторона лессон 7. Правило `feedback_observable_init_preservation.md` существовало с предыдущего инцидента, но **не было автоматизировано**. Guardian/check_design_system.sh не имел grep на `@Observable class` + `let appState` + `init(`. Сегодня оно стало автоматизировано (см. лессон 7).

**Мета-правило** (уже есть в хрониклере, подтверждается): **правила в auto-memory должны быть продублированы в сканере.** Auto-memory полагается на Claude, читающего её в каждой сессии — но когда рабочая сессия растягивается на часы и меняет десятки файлов, внимание рассеивается. Сканер бежит за 2 секунды.
