## Паттерны и уроки

### 1. FK-violation: синтетические id ботов/боссов уходили в `winner_id` / `loser_id`

**Что произошло:** `/api/pvp/match/complete` писал `defenderProxy.id` (синтетический `bot-...` / `boss-...` id из `opponentSnapshot` JSON) прямо в `pvp_matches.winner_id` / `loser_id`. Эти колонки FK-constrained на `characters.id`, которой для ботов просто нет. Каждый бой с ботом падал 500 → "Failed to complete match" на iOS после последнего раунда. Прод потребовал ручной очистки двух зависших `in_progress` матчей через Supabase MCP.

**Корень:** iOS-ответ (`result.winner_id`) и DB-запись шарили одну переменную, хотя у них разные контракты — iOS сравнивает по равенству (синтетический id ОК), БД требует FK-валидный.

**Fix:** Split id-пар на две: `winnerId`/`loserId` для response и `winnerCharacterId`/`loserCharacterId` для DB, с NULL для не-PvP стороны.

**Обновлено:** Добавлена секция §11d в `oracle/SKILL.md` с паттерном и grep-шаблоном для аудита всех combat-эндпоинтов, которые пишут в `pvp_matches` / `pve_matches`. Для будущих правок: при добавлении ветки `isPvp === false` в combat-route — аудит Prisma-write сайтов FIRST, до отправки.

### 2. Snapshot-restore 4-й раз уничтожает static-catalog таблицу

**Что произошло:** прод `appearance_skins` оказался пуст (0 строк) → `/api/appearances` возвращал `{ skins: [] }` → экран "Choose Your Appearance" встал: `selectedSkinKey` остался nil, кнопка Next заблокирована, hero-card без аватара. Миграция `20260420_seed_appearance_skins` пересеяла 40 дефолтных скинов идемпотентно (`ON CONFLICT (skin_key) DO NOTHING`) + новый `seed-appearances.ts` для local/CI.

**Паттерн:** тот же класс, что Gold Mine 2026-04-11, Stash 2026-04-13, Degon admin role 2026-04-19. Четыре раза подряд восстановление из снапшота тихо роняет статический каталог, который был заполнен руками или одноразовым SQL.

**Корень:** источник истины для каталога живёт только в снапшоте, идемпотентного сида нет — более старый снапшот уже не содержит того, что было добавлено «руками после».

**Обновлено:** Новая секция `§6c Post-Restore Static-Catalog Audit` в `gatekeeper/SKILL.md`. Включает:
- Таблицу всех 4 инцидентов с датой и симптомом
- Требование: каждый static-catalog имеет ОБА идемпотентных сида — `.sql` миграция + `seed-*.ts`, с «source of truth» комментарием сверху
- Чеклист SQL-запросов, которые нужно прогнать после любого snapshot-restore: row counts по известным risky-каталогам + admin-role spot check
- Правило: при добавлении нового static-catalog — миграция + seed-скрипт обязаны лэндиться вместе. Ad-hoc `INSERT` через MCP больше не допустим как single source.

### 3. Matchmaking sparse-pool fallback (инфо, без нового правила)

`MIN_OPPONENTS = 3`: если реальный пул < 3 — добиваем ботами до `MAX_OPPONENTS` независимо от `shouldFaceBots` (который keyed off `pvpWins+pvpLosses`). Это закрывает сценарий «post-reset + off-peak → пустая Arena», который аукнулся именно на вчерашнем restore. Никакого нового правила не требует — это компенсирующий паттерн уровня §11b (defensive reads) из `oracle/SKILL.md`.
