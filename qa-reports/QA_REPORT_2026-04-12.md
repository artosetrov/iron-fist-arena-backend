## CRITICAL ISSUES (7)

### BUG-C01 · Double-Tap Fight Button Allows Concurrent Battles
**Screen:** Arena → Fight button
**Reproduce:** Tap "FIGHT" twice rapidly (< 100ms apart)
**Expected:** Only one fight starts; second tap ignored
**Actual:** Two concurrent `/pvp/prepare` requests fire. `fightingOpponentId` guard is set AFTER the async prepare call begins, so both calls pass the guard before either writes the lock flag.
**Root Cause:** ArenaViewModel.fight() — guard check not atomic with the async prepare call
**Impact:** Duplicate battles, double stamina consumption, double rewards
**Fix:** Set `fightingOpponentId = opponentId` as the FIRST line of fight(), before any async work. Add server-side idempotency (reject two prepares from same character within 500ms).

### BUG-C02 · Contraband Gold Payment Race Condition
**Screen:** Shop → Contraband Widget ("The Scavenger")
**Reproduce:** Tap "Claim" rapidly 2-3 times on a paid contraband drop
**Expected:** Single gold deduction, single claim
**Actual:** Optimistic gold deduction happens on line 194 BEFORE `isClaimingContraband = true` on line 187. Two simultaneous calls both pass the guard, both deduct gold optimistically, but only one server claim succeeds. Player loses gold without getting loot.
**Root Cause:** ShopViewModel.claimContraband() — isClaimingContraband set after deduction, not before
**Impact:** Direct gold loss; economy trust broken
**Fix:** Set `isClaimingContraband = true` BEFORE the affordability check and optimistic deduction. Add server-side idempotency key (UUID) to claim request.

---

### BUG-C03 · Shop Item Purchase Double-Tap Exploit
**Screen:** Shop → Buy any item
**Reproduce:** Tap "Buy" twice rapidly on any shop item
**Expected:** One purchase, correct gold deduction
**Actual:** `buyingItemId` guard at line 362 can be passed by two simultaneous taps reading `nil` before either writes. Two `/api/shop/buy` calls fire. Backend uses FOR UPDATE locks (correct), so both may succeed if different items, or one fails if same item. Client optimistic UI shows single deduction but state diverges.
**Root Cause:** ShopViewModel.buy() — buyingItemId assignment after guard, not before
**Impact:** Duplicate items, economy inflation
**Fix:** Move `buyingItemId = item.id` to line 361 (before guard body). Add APIClient-level deduplication (same endpoint + same body within 100ms → cached response).

### BUG-C04 · Guest Account Data Loss on Upgrade Failure
**Screen:** UpgradeGuestView → Apple/Google sign-in
**Reproduce:** Start guest upgrade, simulate network error mid-request (kill connection after Supabase auth succeeds but before Prisma update)
**Expected:** Atomic: either full upgrade or full rollback
**Actual:** If Supabase auth succeeds (new user created) but the Prisma `character.updateMany()` fails, the user is logged into the new account but characters still belong to the old guest userId. Characters are orphaned — effectively lost.
**Root Cause:** No transactional guarantee between Supabase user creation and Prisma character re-parenting
**Impact:** Complete character data loss for guest players upgrading accounts
**Fix:** Wrap character re-parenting in a Prisma transaction. Add a recovery script to detect orphaned guest characters by email match. Implement client retry with exponential backoff.

### BUG-C05 · Race Condition: Multiple Character Create Requests
**Screen:** Onboarding → SAVE button
**Reproduce:** Rapidly tap SAVE twice before first request returns
**Expected:** Second request blocked
**Actual:** `isCreating` guard exists but is not atomic with the API call. Two create requests can reach the backend. The `@unique` constraint on `characterName` rejects the second, but the user sees a confusing "Character name already taken" error instead of "Character already created."
**Root Cause:** OnboardingViewModel.createCharacter() — guard not atomic
**Impact:** Confusing UX; potential for partial creation if constraint isn't unique on all fields
**Fix:** Add a client-side cooldown (1s minimum between create calls). Backend: detect duplicate by checking if the name belongs to the same user before returning error.

### BUG-C06 · Missing Task Cancellation on NavigationStack Pop (Systemic)
**Screen:** ALL screens with async operations
**Reproduce:** Enter any screen (Arena, Shop, Minigames), start a long async operation, pop back to Hub, re-enter screen
**Expected:** All in-flight tasks cancel when view dismisses
**Actual:** ViewModels launch Task objects without storing cancellation references. Tasks continue running after navigation, causing stale API responses to overwrite fresh data, memory leaks, and SFX playing invisibly.
**Root Cause:** No Task storage or cancellation pattern across ViewModels
**Impact:** Memory leaks, stale data overwrites, phantom SFX, race conditions on re-entry
**Fix:** Store all Task references in ViewModels. Cancel in `deinit` or `.onDisappear`. Add `guard !Task.isCancelled` checks in loops (especially CombatViewModel.play()).

### BUG-C07 · Gold Mine Minigame Validation Bypass
**Screen:** Gold Mine → Collect
**Reproduce:** Call `/slot-minigame/submit` endpoint directly (via API) without actually playing the minigame — set `minigame_played_at` in < 500ms
**Expected:** Server validates that real minigame interaction occurred
**Actual:** Backend writes `minigame_played_at` based solely on the submit request, with no validation of actual gameplay. A bot can mark minigame as played instantly, then collect gold without interaction.
**Root Cause:** No server-side proof-of-play validation on minigame submit
**Impact:** Gold inflation via automated farming
**Fix:** Require minimum interaction time (500ms). Add a cryptographic challenge token from `/start` that must be returned in `/submit`. Track interaction patterns for bot detection.

## MAJOR ISSUES (16)

### BUG-M01 · HP Sync Gap Between Combat Finish & Result Screen
**Screen:** CombatDetailView → CombatResultDetailView
**Reproduce:** Complete PvP fight, observe HP display on result screen
**Expected:** Result screen shows post-combat HP immediately
**Actual:** HP from server resolve is applied async AFTER navigation to result screen. Stale HP visible for 1-2 seconds.
**Fix:** Update `appState.currentCharacter.currentHp` from resolve response BEFORE navigating to result.

### BUG-M02 · Loot Not Persisted if Resolve Response Fails
**Screen:** CombatResultDetailView → inventory
**Reproduce:** Win PvP fight with loot, simulate network error on `/pvp/resolve`
**Expected:** Loot queued even if resolve fails
**Actual:** Loot only comes from resolve response. If it fails, `appState.pendingLoot` is never populated. Loot is lost.
**Fix:** Move loot generation to `/pvp/prepare` response, or persist server-side and reconcile on app restart.

### BUG-M03 · HP 30% Gate Not Checked Inside Transaction
**Screen:** Arena → Fight
**Reproduce:** Player at 29% HP, heals to 31% between prepare and fight, fight succeeds
**Expected:** HP gate enforced at fight time, not just prepare time
**Actual:** `/pvp/fight` checks HP only in optimistic pre-check, not inside the FOR UPDATE transaction.
**Fix:** Re-check HP inside the transaction after acquiring the row lock.

### BUG-M04 · Potion Usage Broken — ConsumableInventory Not Wired
**Screen:** Inventory → Use Potion
**Reproduce:** Buy stamina potion from shop, go to Inventory, search for potion
**Expected:** Potion visible and usable
**Actual:** Potions from shop go to `consumableInventory` table, but Inventory screen only reads `equipmentInventory`. The `/api/inventory/use` endpoint only knows about `equipmentInventory`. Potions can't be used from inventory.
**Fix:** Create `/api/inventory/use-consumable` endpoint. Update Inventory screen to fetch and display `consumableInventory`.

### BUG-M05 · Shop Response Nesting Inconsistency (flat vs nested)
**Screen:** Shop → any purchase
**Reproduce:** Compare response shapes: `/shop/buy` returns `{ character: { gold, gems } }` (nested), `/shop/buy-gems` returns `{ gold, gems }` (flat)
**Expected:** Consistent response shape
**Actual:** `ShopService.updateCharacter()` reads flat `response["gold"]` but `/shop/buy` nests it under `character`. Gold/gems silently fail to update after equipment purchases.
**Fix:** Standardize all purchase endpoints to flat `{ gold, gems, ... }`.

### BUG-M06 · Contraband Loot Double-Claim (Missing Unique Constraint)
**Screen:** Shop → Contraband → Claim
**Reproduce:** Network retry sends two identical POST `/api/shop/contraband` with same claimNumber
**Expected:** Second request rejected as duplicate
**Actual:** If no unique constraint on `(characterId, claimNumber)`, a duplicate claim record is created. Player gets double loot.
**Fix:** Add unique constraint on `(characterId, claimNumber)` in Prisma schema. Use upsert instead of create.

### BUG-M07 · GameDataCache Never Explicitly Invalidated After Mutations
**Screen:** Inventory, Shop, Quests (all cached screens)
**Reproduce:** Equip item → close inventory → reopen → stale data until next /game/init
**Expected:** Cache invalidated after mutation
**Actual:** `appState.invalidateCache()` exists but is never called after equip/unequip/upgrade/quest-complete.
**Fix:** Call `invalidateCache("inventory")` after every equip/unequip/upgrade mutation.

### BUG-M08 · Multiple Simultaneous API Calls Overwrite State (Tab Switching)
**Screen:** Arena (OPPONENTS/REVENGE/HISTORY tabs)
**Reproduce:** Rapidly tap OPPONENTS → REVENGE → OPPONENTS. Three Tasks launch without cancellation.
**Expected:** Only most recent load completes
**Actual:** All three complete in arbitrary order. Last-to-complete wins, potentially showing stale data.
**Fix:** Store `loadTask` reference, cancel previous before starting new tab load.

### BUG-M09 · No Loading State While Fetching Tab Data
**Screen:** Arena, Leaderboard, Minigames (tab-based screens)
**Reproduce:** Switch tabs on slow network (3G)
**Expected:** Spinner appears while loading
**Actual:** Stale data remains visible for 2+ seconds with no loading indicator.
**Fix:** Add `isLoadingTab` flag to ViewModels, show ProgressView during loads.

### BUG-M10 · Session Expired Modal Doesn't Clear Auth State
**Screen:** Global (any 401 response)
**Reproduce:** Let token expire, trigger any API call, SessionExpiredModal appears, tap "Log In Again"
**Expected:** User returned to login screen
**Actual:** Modal dismisses but there's no explicit `appState.currentScreen = .auth`. User may remain on dead game screen.
**Fix:** Ensure "Log In Again" calls `appState.logout()` which must set `currentScreen = .auth`.

### BUG-M11 · 401 Handler Not Guaranteed MainActor Timing
**Screen:** Global auth layer
**Reproduce:** Token expires, API returns 401, observe SessionExpiredModal appearance timing
**Expected:** Modal appears within 1 frame
**Actual:** `onUnauthorized` callback runs in actor context, needs nested `Task { @MainActor in }`. Modal may appear 50-200ms late.
**Fix:** Refactor to ensure 401 always triggers @MainActor work synchronously.

### BUG-M12 · XP Overflow at Max Level — No Player Notification
**Screen:** Progression system
**Reproduce:** Hit level 50 (max), earn more XP
**Expected:** Player told to prestige
**Actual:** Backend preserves XP correctly but sends no `atMaxLevel` flag. Client doesn't know to show prestige prompt.
**Fix:** Add `atMaxLevel: boolean` to LevelUpResult response. Client shows prestige prompt when true.

### BUG-M13 · Appearance Selection Resets on Back Navigation
**Screen:** Onboarding → Appearance step
**Reproduce:** Select Orc + Female + specific avatar → Back → Forward
**Expected:** Previous selection preserved
**Actual:** `onGenderChanged()` resets `avatarIndex = 0`. Thumbnail carousel resets to first skin.
**Fix:** Preserve `selectedSkinKey` across origin/gender changes; find matching index in new filtered list.

### BUG-M14 · NPC Guide Widgets Reappear After Dismissal
**Screen:** Arena, Hub (NPC overlays)
**Reproduce:** Dismiss NPC guide → pop screen before UserDefaults flushes → re-enter screen
**Expected:** Guide stays dismissed
**Actual:** UserDefaults write may not flush before view pops. Guide reappears on re-entry.
**Fix:** Call `UserDefaults.standard.synchronize()` immediately after setting dismissal flag.

### BUG-M15 · /game/init — No Partial Failure Handling
**Screen:** Hub initialization
**Reproduce:** Backend returns malformed inventory JSON while character JSON is valid
**Expected:** Entire init fails atomically; cache unchanged
**Actual:** Character parse succeeds and is cached. Inventory parse fails. Hub shows partial data.
**Fix:** Decode ALL data first, validate, THEN update cache atomically.

### BUG-M16 · /api/quests/daily FOR UPDATE Has No Lock Timeout
**Screen:** Daily quest claim
**Reproduce:** Two players claim same quest simultaneously
**Expected:** Fast failure (3-5s timeout)
**Actual:** Second request hangs indefinitely waiting for row lock (30s default timeout)
**Fix:** Add `SET lock_timeout = '5s'` before the FOR UPDATE query.

## MEDIUM ISSUES (5)

### BUG-D01 · Token Refresh Race — Parallel 401 Responses
**Reproduce:** Two simultaneous requests both get 401, both attempt token refresh
**Fix:** Use a shared `refreshInProgress: Task` — second caller awaits the first.

### BUG-D02 · CombatViewModel Play Loop Ignores Task.isCancelled
**Reproduce:** Pop combat view mid-animation — SFX continues playing invisibly
**Fix:** Add `guard !Task.isCancelled` at top of turn loop.

### BUG-D03 · Toast Deduplication by Title Alone
**Reproduce:** Two different errors with same title → first toast removed
**Fix:** Deduplicate by `(title + type + subtitle)` tuple.

### BUG-D04 · GameInitService Parallel Loads Don't Fail Atomically
**Reproduce:** One of 13 parallel /game/init queries fails → partial cache
**Fix:** Use `Promise.allSettled` on backend, report which query failed.

### BUG-D05 · Silent Combat Result Mismatch (Anti-Cheat UX)
**Reproduce:** Client combat engine disagrees with server verdict
**Fix:** Show player an info toast: "Battle result verified by server."
